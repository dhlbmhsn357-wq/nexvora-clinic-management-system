أنت Product Designer + UX Architect. أمامك **Prototype موجود بالفعل على Figma لنظام عيادة/مركز عيادات**.

## المهمة
لا تبدأ من الصفر ولا تعِد بناء النظام بالكامل.

ابدأ أولًا بـ:
1. فحص جميع الشاشات والـComponents والـFlows الموجودة.
2. فهم ما تم تنفيذه بالفعل.
3. الاحتفاظ بكل جزء جيد وقابل لإعادة الاستخدام.
4. تحسين الـUX والـInformation Architecture والـVisual Consistency.
5. إضافة **فقط** الشاشات أو الحالات أو التدفقات الضرورية الناقصة.
6. عدم تكرار شاشة تؤدي نفس الوظيفة الموجودة حاليًا.

الهدف النهائي: Prototype واقعي قابل للعرض على عميل لمركز عيادات، يغطي دورة التشغيل الأساسية بين:

- المريض
- الطبيب
- السكرتير/الاستقبال
- مدير النظام

# 1. Patient — المريض

## السيناريو الأساسي
يدخل المريض للنظام → يبحث عن التخصص/الطبيب → يرى المواعيد → يحجز → يتابع الحجز → يزور العيادة → يرى ملخص الزيارة والوصفة والطلبات اللاحقة.

## المطلوب فقط عند الحاجة
### Home
- التخصصات.
- الأطباء.
- أقرب موعد متاح.
- الحجوزات القادمة.
- اختصارات عملية فقط.

### Search & Doctor Profile
- البحث حسب الطبيب أو التخصص.
- بيانات الطبيب الأساسية.
- العيادة/الفرع.
- سعر الكشف إن كان موجودًا بالنظام.
- المواعيد المتاحة.

### Appointment Booking
Flow واضح:
`اختيار التخصص → الطبيب → الفرع → اليوم → الموعد → تأكيد`

اعرض قبل التأكيد:
- الطبيب.
- المكان.
- التاريخ والوقت.
- نوع الزيارة: كشف جديد / متابعة، إذا كان النظام الحالي يدعمها.
- السعر إن كان موجودًا.

### My Appointments
States:
`Upcoming / Completed / Cancelled`

Actions حسب الحالة:
- عرض التفاصيل.
- إلغاء أو إعادة جدولة قبل الموعد إذا كانت سياسة المركز تسمح.
- معرفة حالة الحجز.

### Visit Result
بعد انتهاء الكشف يستطيع رؤية:
- ملخص الزيارة.
- التشخيص إذا كان مسموحًا للمريض.
- الروشتة.
- التحاليل/الأشعة المطلوبة.
- موعد المتابعة القادم.

### Profile
- البيانات الشخصية.
- بيانات التواصل.
- تاريخ الحجوزات والزيارات الأساسية.

لا تحول حساب المريض إلى EMR معقد؛ اعرض له فقط ما يحتاجه فعليًا.

# 2. Doctor — الطبيب

## السيناريو الأساسي
يسجل الدخول → يرى يومه → يعرف المرضى القادمين والمنتظرين → يفتح المريض → يراجع تاريخه الضروري → يبدأ الكشف → يسجل النتيجة → يكتب الوصفة/الطلبات → ينهي الزيارة.

## Doctor Dashboard
ركز على **اليوم الحالي**:
- عدد مواعيد اليوم.
- المريض الحالي.
- التالي.
- المرضى المنتظرون.
- الحالات المكتملة.
- أي تنبيه مهم يحتاج قرار الطبيب.

تجنب Dashboard مليئة بإحصائيات لا تساعده أثناء العمل.

### Today's Schedule
Timeline أو Queue واضحة:
`Booked → Arrived → Waiting → In Consultation → Completed / No-show`

لكل مريض:
- الاسم.
- وقت الموعد.
- نوع الزيارة.
- حالة الوصول.

### Patient Clinical Profile
عند فتح المريض:
- البيانات الأساسية.
- سبب الزيارة.
- الزيارات السابقة المهمة.
- الأمراض/الحساسيات المهمة إذا كان النظام يدعمها.
- الأدوية الحالية عند الحاجة.
- نتائج التحاليل أو الأشعة المرتبطة.

اعرض المعلومات بطريقة مختصرة ولا تجعل الطبيب يبحث في صفحات كثيرة أثناء الكشف.

### Consultation Workspace
يفضل أن تكون شاشة عمل واحدة تشمل:
- Chief Complaint / سبب الزيارة.
- Notes.
- Diagnosis.
- Prescription.
- Lab Requests.
- Radiology Requests.
- Follow-up.
- زر واضح: **إنهاء الزيارة**.

### Prescription
- إضافة دواء.
- الجرعة.
- عدد المرات.
- المدة.
- تعليمات مختصرة.
- إمكانية التعديل/الحذف قبل الحفظ.

### Complete Visit
عند الإنهاء:
- حفظ السجل.
- تغيير حالة الموعد إلى Completed.
- إتاحة ملخص الزيارة للمريض حسب الصلاحيات.
- إظهار المتابعة المطلوبة إن وجدت.

# 3. Secretary / Reception — السكرتير أو الاستقبال

## السيناريو الأساسي
يبدأ يومه → يرى جدول المركز → يسجل وصول المرضى → ينشئ أو يعدل الحجز → ينظم قائمة الانتظار → يحول المريض للطبيب → يتابع التأخير وعدم الحضور.

هذا الدور **تشغيلي جدًا**؛ صمم له أقل عدد ممكن من الخطوات.

### Reception Dashboard
اعرض:
- مواعيد اليوم.
- وصل.
- منتظر.
- داخل الكشف.
- انتهى.
- متأخر.
- No-show.

مع Quick Actions:
- حجز جديد.
- تسجيل مريض.
- Check-in.
- إعادة جدولة.

### Calendar / Appointments
Calendar يومي/أسبوعي مناسب للتشغيل.

يجب أن يرى السكرتير:
- الطبيب.
- المريض.
- الوقت.
- نوع الحجز.
- الحالة.

### Create Appointment
في Flow واحد قدر الإمكان:
`بحث عن المريض أو إضافة جديد → الطبيب → الفرع/العيادة → الموعد → تأكيد`

لا تجبر المستخدم على إنشاء الحجز ثم فتح شاشة أخرى لاستكمال الجدولة.

### Patient Check-in
عند وصول المريض:
`Booked → Arrived → Waiting`

ثم يتم إدراجه تلقائيًا في Queue الطبيب.

### Queue Management
قائمة واضحة لكل طبيب:
- الحالي.
- التالي.
- المنتظرون.
- وقت الانتظار التقريبي إذا كان يمكن حسابه.
- تأخير الطبيب إن وجد.

### Appointment Actions
- إعادة جدولة.
- إلغاء.
- No-show.
- تغيير الحالة.
- فتح ملف المريض الإداري.

### Patient Administrative Profile
السكرتير يرى فقط البيانات اللازمة للتشغيل:
- الاسم.
- الهاتف.
- الحجوزات.
- بيانات الدفع الأساسية إن وجدت.

لا تعرض له الملاحظات الطبية السرية إلا إذا كانت الصلاحيات الحالية تسمح بذلك.

# 4. System Manager / Admin — مدير النظام

## السيناريو الأساسي
يدخل → يعرف حالة تشغيل المركز → يرى ما يحتاج تدخلًا → يدير الأطباء والجداول والفروع والخدمات والمستخدمين → يراجع الأداء والتقارير.

### Executive / Operations Dashboard
يجب أن يجيب بسرعة عن:
- كم مريض اليوم؟
- كم زيارة تمت؟
- كم No-show؟
- هل يوجد ضغط أو تأخير عند طبيب؟
- هل يوجد طبيب غائب أو جدول متعارض؟
- ما المواعيد أو المشاكل التي تحتاج تدخلًا؟

لا تضف KPIs لمجرد ملء الصفحة.

### Doctors Management
- إضافة/تعديل طبيب.
- التخصص.
- الفروع التي يعمل بها.
- أيام وساعات العمل.
- مدة الكشف.
- الطاقة اليومية أو Slot Duration.
- حالة الحساب.

### Schedule Management
إدارة:
- جداول الأطباء.
- الإجازات.
- الفروع.
- أوقات العمل.
- الاستثناءات.
- منع تضارب المواعيد.

### Branches / Clinics
إذا كان النظام Multi-branch:
- الفروع.
- العيادات/الغرف.
- الأطباء المرتبطون بها.
- الخدمات المتاحة.

### Services
إدارة:
- التخصصات.
- أنواع الزيارة.
- مدة كل خدمة.
- السعر إذا كان النظام يدعم الدفع.

### Users & Permissions
أدوار مثل:
- Admin.
- Doctor.
- Receptionist.

مع Role-Based Permissions واضحة، ولا تعتمد على إخفاء الزر فقط؛ كل Role يجب أن يرى ويفعل فقط ما يحتاجه.

### Reports
ركز على التقارير العملية:
- عدد الحجوزات والزيارات.
- الإلغاءات وNo-show.
- أداء/إشغال الأطباء.
- أوقات الانتظار.
- الإيرادات فقط إذا كان النظام الحالي يحتوي على جزء مالي.

Filters:
`الفترة / الطبيب / التخصص / الفرع`

# 5. Core System Logic

استخدم حالات موحدة للمواعيد:

`Booked → Confirmed → Arrived → Waiting → In Consultation → Completed`

وحالات استثنائية:
`Cancelled / Rescheduled / No-show`

يجب أن ينعكس تغيير الحالة فورًا بين:
- المريض.
- الطبيب.
- السكرتير.
- لوحة الإدارة.

مثال:
عندما يعمل Receptionist للمريض Check-in:
- يتحول إلى Arrived/Waiting.
- يظهر في Queue الطبيب.
- تتحدث Dashboard الاستقبال.
- لا يحتاج إدخال الحالة يدويًا مرة ثانية في شاشة أخرى.

# 6. UX Rules

- أي عملية متكررة يجب أن تتم بأقل عدد خطوات ممكن.
- استخدم Progressive Disclosure بدل حشر كل المعلومات.
- لا تنشئ صفحات كثيرة إذا كان Tabs / Drawer / Modal يحل المشكلة أفضل.
- اجعل Today's Work أهم من الإحصائيات لكل من الطبيب والسكرتير.
- استخدم Empty / Loading / Error / Success / Disabled States.
- أضف Confirmations فقط للعمليات الخطرة مثل الإلغاء والحذف وإنهاء الزيارة.
- اجعل البحث والفلاتر عملية وسريعة.
- صمم Desktop أولًا للسكرتير والإدارة والطبيب إن كان النظام الحالي Desktop، مع Responsive منطقي.
- حافظ على Design System الموجود إذا كان جيدًا، وقم بتوحيده بدل استبداله بلا سبب.

# 7. مهمة التطوير على الـFigma الحالي

قبل إضافة أي Frame جديد:

**Existing → Keep / Improve / Merge / Missing**

صنف الشاشات الحالية داخليًا بهذه الطريقة.

ثم:
- Keep: احتفظ بالجيد.
- Improve: حسن UX أو hierarchy.
- Merge: ادمج الشاشات المكررة أو المجزأة دون داعٍ.
- Missing: أنشئ الناقص فقط.

استخدم نفس:
- Components
- Tokens
- Typography
- Grid
- Icon system

كلما كانت مناسبة.

إذا كانت الهوية الحالية ضعيفة، حسنها تدريجيًا دون تغيير المنتج كله لمجرد تغيير الشكل.

# المطلوب النهائي

أنشئ Prototype متصل End-to-End يحتوي على 4 سيناريوهات قابلة للتجربة:

### Patient Flow
`Home → Search Doctor → Select Slot → Book → Appointment → Visit Result`

### Doctor Flow
`Today → Patient Queue → Patient Profile → Consultation → Prescription → Complete Visit`

### Reception Flow
`Today's Appointments → New/Existing Patient → Booking → Check-in → Queue → Complete Operational Flow`

### Admin Flow
`Dashboard → Doctors → Schedule → Users/Permissions → Reports`

لا تضف Features غير ضرورية مثل AI أو CRM ضخم أو Inventory أو Insurance أو Pharmacy أو Accounting أو Telemedicine ما لم تكن موجودة أصلًا في الـPrototype الحالي أو مطلوبة صراحة.

**الأولوية:**
وضوح التشغيل > كثرة المميزات  
اكتمال الـFlow > كثرة الشاشات  
إعادة استخدام الموجود > إعادة البناء  
حل مشاكل المستخدم > الشكل الاستعراضي فقط
